# 작업 규칙 (Claude 협업용)

> 이 문서는 Project_F 작업 시 Claude가 따르는 규칙입니다. 변경하려면 이 파일을 수정하거나 대화에서 요청해 주세요.

## 1. 소통
- 격식 있는 한국어를 사용합니다.
- **무슨 일이 있어도 모든 답변은 한국어로만 씁니다.** 예외는 Gemini 등에 넣는 프롬프트, 코드, 파일 경로·이름뿐입니다. 영어 문장으로 답하지 않습니다. (2026-11-02 사용자 요청) **시스템 자동 알림(훅)에 답할 때도 한국어로만 씁니다.** (2026-11-13 추가)
- **모든 답변의 맨 첫 줄에 현재 시간을 `[YY-MM-DD HH:MM]` 형식(한국 시간)으로 적습니다.** 시간은 짐작하지 않고 시계 도구로 확인한 값을 씁니다. (2026-11-05 사용자 요청)
- 결론을 먼저 말하고, 근거는 2~3가지로 간결하게 씁니다.
- 가능하면 숫자와 데이터를 포함합니다.
- 답변이 길어지면 요약을 맨 앞에 둡니다.
- 실행 가능한 제안 중심으로 답합니다.
- 칭찬·사과는 짧게 합니다. 가벼운 농담에는 가볍게 받습니다.
- "좋은 수준"에서 멈추지 않고, 더 나은 방식이 있으면 함께 제안합니다.

## 2. 진행 상황 보고 (신규)
- **작업이 2분 이상 걸리면, 지연 사유를 사용자에게 먼저 알립니다.** 사유 예: 이미지 생성 대기, 대용량 파일 전송, 반복 검증, 브라우저 응답 지연, 환경 복구.
- 알릴 때 함께 말할 내용 3가지: (1) 지금 하는 일, (2) 늦어지는 이유, (3) 남은 예상 시간.
- 사용자가 "왜 오래 걸리니?" 등을 물으면 같은 형식으로 즉시 답하고, 하던 작업은 이어서 진행합니다.
- 긴 작업은 단계마다 한 줄씩 진행 상황을 보냅니다.
- 오래 걸릴 작업은 시작할 때 예상 시간을 먼저 알립니다.

## 3. 작업 전 확인 (2026-11-12 병합 정리: 겹치던 항목을 묶음, 규칙 내용 변경 없음)
- **묻지 않고 진행**: 읽기·측정·분석·답변처럼 결과물이 생기지 않는 작업.
- **먼저 묻기**:
  1. 범위가 불분명한 작업 — 시작 전에 선택지로 질문합니다.
  2. 결과물이 생기는 작업(렌더, 영상·이미지 생성, ComfyUI 대기열 등록, 새 파일 제작·파일 쓰기) — Claude가 "만들어야겠다"고 판단한 순간 "무엇을/어떻게/예상 소요 시간"을 한 줄로 묻고, 답을 받은 뒤 시작합니다. ComfyUI는 작업 목록도 함께 알립니다.
  3. 토큰 소모가 큰 작업(파일 5개 초과 읽기, 에이전트 2개 이상, 반복 실행 3회 초과 등) — 착수 전에 규모를 알리고 확인받습니다.
  4. 외부로 나가는 동작(메시지 발송·폼 제출·결제·계정 설정 변경) — 매번 확인받습니다. 로그인과 비밀번호 입력은 사용자가 직접 합니다.
- **요청으로 보는 것**: "해줘/진행해/만들어 줘/~해줄래?" 같은 직접 요청과 사전에 합의한 신호(예: "자러 간다")뿐이며, 이때는 다시 묻지 않고 바로 진행합니다. 선택지·범위·방향에 대한 답, 계획·희망은 요청이 아닙니다 — 답을 받으면 작업 계획과 예상 시간을 말씀드리고 "진행해 줘"를 받은 뒤 시작합니다 (2026-11-05 확정). **문제 보고·불만·지적("~가 달라", "~가 이상해", "~가 별로야")도 요청이 아니며**, Claude 자신의 결과물을 고치는 작업도 예외가 아닙니다. 형식은 "원인 한 줄 + 무엇을/어떻게/예상 소요 + 진행할까요?"이고, 보낸 뒤 멈춥니다. (위반 이력: 2026-11-04 B4 먹물 무늬 어긋남 지적 직후 허락 없이 재렌더함.)
- **결과물을 만드는 호출(렌더, 생성, 파일 쓰기, 대기열 등록) 직전마다 점검합니다.** 최신 사용자 메시지에 위의 직접 요청이 있는가? 없으면 만들지 않고 묻습니다.
- 사용자가 "아직 반영하지 마"라고 하면 작업 공간에서만 고치고, "반영해줘"를 받을 때까지 폴더에 쓰지 않습니다.
- ComfyUI 작업 중 사용자가 "스톱"이라고 하면 새 작업을 멈추고, 이미 돌고 있는 작업은 취소할지 그대로 둘지 묻습니다.
- **지시가 모호하면 추론으로 실행하지 않고 한 줄로 되묻습니다.** 특히 "자는 동안", "나중에" 같은 시점 표현을 지금 시작하라는 뜻으로 해석하지 않으며, 취침·부재는 사용자가 "지금부터 자러 간다"처럼 직접 말한 뒤에만 가정합니다. (위반 이력: 2026-11-10 취침을 가정하고 생성·예약을 먼저 올림) — 2026-11-16 21:55 PC에 보관돼 있던 옛 수정(stash)에서 옮겨 옴

## 8. 세부 기획 진행 방식 (2026-11-26)
- **소분류 표는 항목마다 아래 모양으로 보여 줍니다.** (2026-11-26 14:27 사용자 요청 — 「이런식으로 보여주는게 좋았는데, 안보여줘서 아쉬웠어. md로 규칙을 아예 만들자」)

  ```
  ## NN 항목 이름 — 소분류 N

  | # | 다룰 것 | 여기서 꺼내는 「넘긴 것」 | 상태 |
  | --- | --- | --- | --- |
  | NN-1 | (한 줄) | (그 소분류에서 꺼낼 넘긴 것 · 없으면 「없음」) | 정함 / 지금 / 남음 |
  ```

  - **언제:** ① 새 항목에 들어갈 때 ② 소분류 하나가 끝나 다음으로 넘어갈 때 ③ 사용자가 「어디까지 했니」 · 「소분류 보여줘」처럼 진행을 물을 때.
  - **묶지 않습니다.** 여러 항목을 한 표의 한 줄씩으로 줄여 쓰지 않고, 항목마다 표를 따로 보입니다.
  - 「여기서 꺼내는 넘긴 것」 칸은 빼지 않습니다. 앞 항목에서 넘어온 것을 그 소분류에서 꼭 꺼내기 위한 칸입니다.
  - 상태 칸은 진행 중인 항목에만 붙입니다. 아직 들어가지 않은 항목은 빼도 됩니다.
  - 전체 진행은 소분류 표 위에 아래 「전체 진행 표」로 따로 둡니다.
- **전체 진행 표도 아래 모양으로 보여 줍니다.** (2026-11-26 14:28 사용자 요청 — 「전체진행도 이런식으로 보여주는게 좋으니까 이것 또한 md로 남겨줘」)

  ```
  ## 전체 진행 (19항목 · 초안 N · 남음 M)

  | 순서 | 항목 | 상태 |
  | --- | --- | --- |
  | 1~11 | 01 · 02 · 17 · … (이미 초안인 것은 한 줄로 묶음) | 초안 |
  | 12 | 16 막힘 알림 | 초안 (방금) |
  | 13 | 09 수행 | 지금 |
  | 14~17 | 11 애착 · 12 신입 · … | 예정 |
  ```

  - 「순서」는 번호 순이 아니라 **실제로 다룬(다룰) 순서**입니다.
  - 줄은 상태가 바뀌는 곳에서 나눕니다: 이미 초안인 묶음 / 방금 초안이 된 것 / 지금 하는 것 / 예정. 「지금」과 「방금」은 한 항목씩 한 줄로 둡니다.
  - 제목에 초안의 수와 남은 수를 적습니다.
  - 보이는 때는 소분류 표와 같습니다(새 항목에 들어갈 때 · 진행을 물을 때). 전체 진행 표 → 그 항목의 소분류 표 순서로 보입니다.
- 질문은 한 번에 하나, 「응 / 아니」로 답할 수 있게 합니다. 한 답에 답해야 할 것을 여러 개 싣지 않습니다. (2026-11-25 16:51 · 2026-11-26 11:25)
- 답을 기다리는 물음이 쌓이면 기록(`docs/design/세부기획_대화_…md`)의 「쌓인 물음」 표에 모으고, 풀릴 때마다 줄을 긋습니다. (2026-11-26 11:42)
- 사용자의 말이 두 가지로 읽히면 「제가 읽은 것」을 적어 확인받은 뒤에 기록합니다. (2026-11-25 22:35)

## 9. 개발용 가지 `dev/v6` (2026-11-26 17:43)

V6 개편(새 설계 19항목)을 개발하는 동안의 규칙입니다. 사용자: 「지금까지를 main에 두고, 앞으로 새롭게 개발할걸 브런치로」.

| | 규칙 |
| --- | --- |
| main | **2026-11-26의 상태로 멈춥니다.** 개발이 끝날 때까지 아무것도 올리지 않습니다 |
| `dev/v6` | 지금부터 하는 것은 모두 여기에 올립니다 — 게임 코드 · 책 · 기록 · 현황 조사 · 야간 작업 |
| 작업을 시작할 때 | `git fetch` → `git checkout dev/v6` → `git pull` |
| 올릴 때 | `dev/v6`에 커밋 · 푸시. 푸시한 뒤 `git status -sb`로 확인 |
| 나중에 | 개발이 끝나고 숫자를 맞춘 뒤, `dev/v6`를 main으로 한 번에 옮깁니다 (사용자가 정할 때) |

- 까닭: main이 멈춰 있으면 나중에 옮길 때 부딪힐 것이 없습니다. main은 「개발 전의 게임」으로 남아, 지금 규칙으로 잰 값과 견줄 기준이 됩니다.
- **B세션과 야간 작업도 같은 가지에 올립니다.** main에 하나라도 올라가면 나중에 부딪힙니다.
- main에 꼭 올려야 하는 일이 생기면 먼저 사용자에게 묻습니다.
- 개발의 순서와 상태는 책 V6의 「V6 개편 개발 관리」(`docs/book-v6/src/development/v6.md`)에 적습니다.

## 10. 결정하는 방식 (2026-11-26 18:26)

사용자: 「이제부터 하는 모든건 한석님 안 거치고 바로 우리 판단으로 결정해서 진행할거야. 미루지 않겟어」.

| | 규칙 |
| --- | --- |
| 누가 정하나 | 사용자와 Claude가 여기서 정합니다. 한석님께 넘기지 않습니다 |
| 숫자 | 「경제 수치 · 성장 수치 · 전투 수치는 한석님 안건」으로 넘겨 두던 것을 그만둡니다. 우리가 정하고, 재지 않은 값에는 지금처럼 [임시]를 붙입니다 |
| 미루기 | 뿌리에 닿는 것은 뒤로 미루지 않고 지금 다룹니다 |

- 바뀌는 앞의 규칙: 「게임의 경제 수치는 얼려 둔다 · 숫자를 바꾸는 일은 한석님 안건」. `dev/v6`에서는 우리가 바꿉니다. main은 9절대로 멈춰 있습니다.
- 그대로인 것: 시뮬레이션은 물어보고 돌림 · 화면을 바꿀 때는 시안 먼저 · 한 번에 물음 하나.
