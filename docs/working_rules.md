# 작업 규칙 (Claude 협업용)

> 이 문서는 Project_F 작업 시 Claude가 따르는 규칙입니다. 변경하려면 이 파일을 수정하거나 대화에서 요청해 주세요.

## 1. 소통
- 격식 있는 한국어를 사용합니다.
- **무슨 일이 있어도 모든 답변은 한국어로만 씁니다.** 예외는 Gemini 등에 넣는 프롬프트, 코드, 파일 경로·이름뿐입니다. 영어 문장으로 답하지 않습니다. (2026-11-02 사용자 요청)
- 결론을 먼저 말하고, 근거는 2~3가지로 간결하게 씁니다.
- 가능하면 숫자와 데이터를 포함합니다.
- 답변이 길어지면 요약을 맨 앞에 둡니다.
- 실행 가능한 제안 중심으로 답합니다.
- 칭찬·사과는 짧게 합니다. 가벼운 농담에는 가볍게 받습니다.
- "좋은 수준"에서 멈추지 않고, 더 나은 방식이 있으면 함께 제안합니다.

## 2. 진행 상황 보고 (신규)
- **작업이 2분 이상 걸리면, 지연 사유를 사용자에게 먼저 알립니다.** 사유 예: 이미지 생성 대기, 대용량 파일 전송, 반복 검증, 브라우저 응답 지연, 환경 복구.
- 알릴 때 함께 말할 내용 3가지: (1) 지금 하는 일, (2) 늦어지는 이유, (3) 남은 예상 시간.
- 사용자가 "왜 오래 걸리니?" 등을 물으면 같은 형식으로 즉시 답하고, 하던 작업은 이어서 진행합니다.
- 긴 작업은 단계마다 한 줄씩 진행 상황을 보냅니다.
- 오래 걸릴 작업은 시작할 때 예상 시간을 먼저 알립니다.

## 3. 작업 전 확인
- 범위가 불분명한 작업은 시작 전에 선택지로 질문합니다.
- 외부로 나가는 동작(메시지 발송·폼 제출·결제·계정 설정 변경)은 매번 확인받습니다. 로그인과 비밀번호 입력은 사용자가 직접 합니다.
- 토큰 소모가 큰 작업(파일 5개 초과 읽기, 에이전트 2개 이상, 반복 실행 3회 초과 등)은 착수 전에 규모를 알리고 확인받습니다.
- **범위나 방향을 고르는 질문에 답을 받은 것은 착수 승인이 아닙니다.** 작업 계획과 예상 시간을 말씀드리고, "진행해 줘"를 받은 뒤에 시작합니다. (2026-11-05 확정)
- 사용자가 "아직 반영하지 마"라고 하면 작업 공간에서만 고치고, "반영해줘"를 받을 때까지 폴더에 쓰지 않습니다.

## 4. Git / 파일 전달
- 커밋과 푸시는 사용자가 GitHub Desktop으로 직접 합니다. Claude는 푸시하지 않습니다.
- 커밋이 필요하면 한국어 커밋 요약을 함께 제공합니다.
- 산출물은 `Project_F` 폴더의 알맞은 위치에 직접 저장합니다.
- 사용자가 수정했을 수 있는 기존 파일을 덮어쓸 때는 변경 여부를 확인한 뒤 씁니다.
- 임시·중간 파일은 프로젝트 폴더에 두지 않습니다.
- 결과물은 저장한 뒤 크기와 내용을 다시 확인합니다. 이미지 결과는 화면으로 보여 줍니다.

## 5. 에셋 제작 (Gemini · GPT 워크플로)
- 한 번에 한 시트씩 만들고, 투명 처리 후 크기·정렬을 검증합니다.
- 생성 이미지는 단색 마젠타 배경으로 받아 크로마키로 투명 처리합니다.
- 최종 에셋은 용량을 최적화(WebP/PNG)하여 `prototype/assets/` 아래에 둡니다.
- 사용자가 직접 생성한 결과가 있으면 그것을 우선 사용합니다.
- **GPT(ChatGPT, Claude 내장 브라우저)**: 프롬프트를 먼저 사용자에게 보여 주고 허락받은 뒤 보냅니다. 같은 그림체가 필요하면 같은 대화에서 이어 요청합니다.
  - 프롬프트에 "Background: real alpha transparency, NOT a drawn checkerboard"를 넣고, 받은 뒤 브라우저 JS로 투명 비율을 확인합니다. 배경이 칠해져 오면 다시 요청합니다.
  - 사용자가 다운로드 폴더에 저장 → 가져와 알파로 잘라 256px 등으로 맞춥니다. 원본 시트는 `art_source/`에 보관합니다.

## 6. 보고
- 작업 완료 시 결과를 한두 문장으로 요약하고, 파일 위치를 알려줍니다.
- 한 일은 짧고 정확하게, 안 한 일은 안 했다고 밝힙니다.
- 직접 측정하지 못한 값은 어림값이라고 밝힙니다.
- 틀리면 바로 인정하고 고칩니다. 지적받은 일은 그 자리에서 이 문서에 규칙 한 줄로 추가할지 제안합니다.
- 다음에 할 일이 있으면 순서대로 제시합니다.

## 7. 팝업·화면 퀄업 진행 방식 (2026-11-05)
- 진행표: `docs/design/popup_quality_todo.md`. 사용자가 "다음 할 거 보여줘"라고 하면 이 표를 갱신해 보여 주고 다음 대상을 안내합니다.
- 순서: ① 지금 화면 캡처 + 문제점(화면 문제와 **코드의 실제 규칙과 어긋나는 점**) → ② 논의(사용자 말을 번호 붙여 받아 적고, 모호하면 선택지로 확인, 추천안은 표로 비교) → ③ 시안(작업 공간에서만 고치고 캡처로 보여 줌. 오버 창·연출은 장면별) → ④ "반영해줘"를 받으면 폴더에 반영.
- 반영할 때: 장치 파일 수정 시각을 확인하고 쓰기 → 다시 받아 비교(`cmp`) → 규칙을 바꿨으면 관문 1(`node tools/gate1_check.js`) → 팝업 설계 문서(`docs/design/popup_*.md`)와 진행표 갱신 → 한국어 커밋 메시지.
- 게임 규칙을 바꾸면 시뮬레이터(`sim_engine.js`)도 같은 규칙으로 바꿉니다. 화면용 기록만 추가할 때는 관문 1 수치가 변하지 않는지 확인합니다.
- 화면에 적힌 효과·수치는 실제 규칙과 같아야 합니다. 구현되지 않은 효과를 적게 되면 "아직 게임에 적용되지 않음"을 사용자에게 먼저 알립니다.
- 시안 캡처는 `tools/dev/popup_shot.js`(사용법: `tools/dev/README.md`). 작은 창(1366×768)에서도 한 번 확인합니다.
- 사용자가 "나중에 리마인드해 줘"라고 한 항목은 진행표 "남은 미결"에 **리마인드 대상**으로 적고, 관련 작업을 시작할 때 먼저 꺼냅니다.
